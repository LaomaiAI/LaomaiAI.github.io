Skill：多 Agent 团队决策（上团队前 5 步）

来源：03《多 Agent 团队决策教程》+ Vals AI《Do Agent Teams Pay Off?》(2026-10-09)、The Decoder 引用的 Anthropic 内部数据。结论供参考，Vals AI 每组配置仅运行一次。

直接把下面的提示词丢给你的 Agent，即可使用这个 Skill。先过检查表，再看两个完整示例，最后按失败回退模板写验收标准。

什么时候用这个 Skill

手头有个任务，犹豫“单 Agent 干，还是上 Agent 团队”时用。目标：5 分钟出结论，不烧冤枉钱。

核心原则

  • 大多数场景，不要上多 Agent 团队。（“大多数”为作者判断，非实测数字。）先把单个 Agent 用到极致。
  • 团队买的是速度，不是质量。
  • 团队成本是单 Agent 的 1.8–5.1 倍（Vals AI 实测口径）。

一、决策清单（可打印检查表）

6 项全部打勾，才考虑上团队。有一项打不上，就单 Agent 干。

□检查项怎么判
☐单个 Agent 推理力度已拉满已跑“默认 + 拉满”两轮对比，拉满仍不够用
☐任务能拆成可独立验收的块每块能写出一句话验收标准，写不出来 = 拆不了
☐缺的是时间，不是质量缺质量 → 别加人；缺时间 → 可考虑加人换速度
☐算过账1.8–5.1 倍成本换速度，值吗？只有“今晚就要交货”才值得
☐Lead 验收标准已写清每个 subagent 的输入、输出、验收标准 + 合并 + 冲突处理 + 回退
☐失败回退已定哪个环节失败、整体怎么回退、谁兜底，已写在下面模板里

二、完整示例 1：上团队（今晚必须交货）

任务：今晚 22:00 前，抓取 5 个竞品官网的价格页，汇总成一张对比表

决策：上团队。理由：5 个站点互相独立，可并行；缺的是时间（今晚就要），不是质量；单个 Agent 逐个抓要 2 小时，团队并行 30 分钟能完。

分工与验收标准（填好的）：

  • Lead：输入 = 5 个 URL + 表头模板；输出 = 一张对比表（5 行 × 表头列）+ 异常清单；验收 = 5 行齐全、价格与截图一致、异常标注来源。
  • Subagent A/B/C/D/E（各 1 个站点）：输入 = 1 个 URL + 抓取字段（价格、套餐名、更新时间）；输出 = 该站 1 行数据 + 页面截图；验收 = 价格数字与截图一致、更新时间注明、抓不到时返回“未找到 + 截图”而不是编一个数。
  • 合并规则：Lead 按表头模板合并，价格单位统一为人民币/月，缺失项填“未找到”并标红，不补默认值。
  • 冲突处理：同一站点两个来源价格不一致时，以官网截图为准，另一来源记入异常清单。
  • 失败回退：任一 subagent 超时 5 分钟，Lead 先用已回的 4 行出表，第 5 行标“待补”，不阻塞交付；全部超时则回退为单 Agent 逐个抓，告知用户延迟 1 小时。

成本账：单 Agent 约 1.22 美元，团队约 3.07 美元（2.5 倍），换今晚准时交货，值。（以 Vals 实测口径为例，非本任务实测。）

三、完整示例 2：不上团队（前后耦合严重）

任务：写一个完整的待办事项 Web 应用（前端 + 后端 + 登录 + 部署）

决策：不上团队。理由：前后耦合严重，拆不开；缺的是质量（要跑通），不是时间；单个 Agent 拉满推理力度已能跑通初版。

为什么拆不了（验收标准写不出来）：

  • 前端依赖后端接口形状，后端依赖数据模型，接口一改，前后都得返工——子任务无法“独立验收”。
  • 试图写验收标准时发现：前端的验收是“页面能增删改查”，前提是后端已就绪；后端的验收是“接口返回正确”，前提是数据模型已定。互相等对方先定，拆不开。
  • 硬拆的结果：Lead 花一半时间在对齐接口、传话、返工，成本 1.8–5.1 倍，质量反而下降（Vals 实测：推理拉满后团队全都没提升）。

正确做法：单 Agent 拉满推理力度，一口气写完初版，跑通后再拆“修 Bug / 加功能”这种可独立验收的小块。

成本账：不上团队省 1.8–5.1 倍成本，质量更高。

四、失败回退模板（复制后填空）


任务：[填入任务]
Lead：[谁负责合并]
合并规则：[按什么模板合并，单位/格式怎么统一，缺失项填什么]
冲突处理：[两个来源不一致时，以哪个为准，另一个记到哪里]
超时规则：[单个 subagent 超时 X 分钟，Lead 怎么处理：先出部分结果 / 等 / 重试]
回退条件：[什么情况下放弃团队模式，回退为单 Agent]
回退动作：[回退后怎么做，谁告知用户，延迟多久]
兜底：[最坏情况下交付什么：部分结果 + 异常清单，不编数]

五、操作清单（照着做）

第 1 步：拉满单个 Agent

  1. 用单个 Agent 跑一遍当前任务，记录质量分 / 是否可用；
  2. 把 reasoning effort 调到最大，再跑一遍，对比；
  3. 如果调高已经够用，停，不要上团队。

第 2 步：判断能不能干净切分

  • 能拆的标准：每个子任务能独立验收。
  • 能拆的例子：“同时抓 5 个网站的数据”；
  • 不能拆的例子：“写一个完整的应用”（前后耦合严重）。
  • 给每块写一句话验收标准。写不出来，就说明拆不了。

第 3 步：问缺什么

  • 缺质量 → 别加人；
  • 缺时间 → 可以考虑加人，用成本换速度。

第 4 步：算账

  • 问：“1.8–5.1 倍成本换来的速度提升，值吗？今晚必须交货，还是明天交也行？”
  • 只有“今晚就要交货”时，才值得花 2.5 倍成本换速度。

第 5 步：写清 Lead 验收标准 + 失败回退

  • 每个 subagent 的输入、输出、验收标准；
  • Lead 怎么验收、怎么合并、怎么处理冲突；
  • 哪个环节失败，整体怎么回退。
  • 没写验收标准 = 小工瞎干。写不出来，就不上。

六、提示词（可复制）

你在帮我决策：这个任务该单 Agent 干，还是上多 Agent 团队？

任务描述：[填入任务]
当前单个 Agent 表现：[填入质量分/是否可用]
推理力度是否已拉满：[是/否]

请按下面 5 步输出结论，不要直接给“上团队”：
1. 单个 Agent 拉满后是否够用？
2. 任务能否拆成“可独立验收”的块？每块写一句话验收标准，写不出来就判为拆不了。
3. 我缺的是质量还是时间？
4. 算账：1.8–5.1 倍成本换速度，值吗？
5. 如果上团队，写清 Lead 的验收标准 + 失败回退模板（合并、冲突、超时、回退）。

最后给一句话结论：上 / 不上 + 理由。
