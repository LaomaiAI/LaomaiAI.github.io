代码 A：直接调 Search & Fetch（按官方文档整理，未实测）

import os
import time
import requests

BASE = "https://api.deepseek.com"
HEADERS = {
    "Authorization": f"Bearer {os.environ['DEEPSEEK_API_KEY']}",
    "Content-Type": "application/json",
}

def search(query, count=5, need_content=False, retries=2):
    for attempt in range(retries + 1):
        r = requests.post(
            f"{BASE}/v1/tools/search",
            headers=HEADERS,
            json={"query": query, "count": count, "need_content": need_content},
            timeout=30,
        )
        if r.status_code in (408, 429, 500, 502, 503, 504) and attempt < retries:
            time.sleep(2 ** attempt)  # 官方文档：408、429、5xx 等一等再重试
            continue
        if r.status_code == 402:
            raise RuntimeError("余额不足（402）：先充值再重试")
        r.raise_for_status()  # 其他 4xx 先改请求，不要盲目重试
        return r.json()["results"]
    raise RuntimeError("搜索重试耗尽")

def fetch(url, retries=2):
    for attempt in range(retries + 1):
        r = requests.post(
            f"{BASE}/v1/tools/fetch",
            headers=HEADERS,
            json={"url": url},
            timeout=30,
        )
        if r.status_code in (408, 429, 500, 502, 503, 504) and attempt < retries:
            time.sleep(2 ** attempt)
            continue
        if r.status_code == 402:
            raise RuntimeError("余额不足（402）：先充值再重试")
        if r.status_code == 404:
            return None  # 抓不到可用正文：目标站不可用、被站方拦、内容类型不支持等
        r.raise_for_status()
        return r.json()
    raise RuntimeError("抓取重试耗尽")

results = search("DeepSeek V4.1-Flash-1017 site:github.com lang:en after:2025", count=5)
good = [x for x in results if x.get("rerank_score", 0) >= 1.5]
for x in good[:3]:
    print(x["rerank_score"], x["title"], x["url"])
    page = fetch(x["url"])
    if page:
        print(page["title"], "正文长度：", len(page["content"]))

要点：count 范围 1 到 50，默认 10，只控制条数，不影响单价；need_content 为 false 时 content 恒为空串；rerank_score 1.5 以上算高质量，authority 3 以上为高权威。来源：官方 Search & Fetch 文档。

完整示例 1：正例（切换做对了）

场景（假设示例，仅演示流程，未实测）：你之前用 deepseek-flash 接在 OpenAI 格式上。

做法：模型名、Base URL、Key、请求格式全部不动。把 Harness 升级到 v0.2.1-rc.1。发一条冒烟请求，确认 HTTP 200、model 回显 deepseek-flash、账单按 Flash 价格计费。工具调用、长上下文、视觉各跑一条。升级 Harness 后跑一条端到端小任务。免费窗口内用服务端工具调用验证搜索质量，确认有用后再把直调接进系统。

结果：切换完成，验证通过，搜索在免费期验证完，评测集冻结并跑完。这就是发布当日的正确顺序。

完整示例 2：反例（搜索接错了）

场景（假设示例，仅演示错误，未实测）：发布当天看到 Search & Fetch 开放，直接把直调写进生产系统，每次用户请求都触发多次搜索和抓取，query 里还带了内部链接。

错在哪：第一，没走免费窗口验证，计费开始后才发现搜索质量不符合预期，钱已经花了。第二，没做限速和节流，5 QPS 一到就开始吃 429。第三，query 带了内部链接，等于把内部信息发给了搜索引擎。第四，关键结论直接用了搜索摘要，没打开原文验。

正确做法：免费窗口内先用服务端工具调用验证；直调接进去之前加节流、重试、用量上限；query 只写公开可查的内容；关键结论打开原文验。

完整示例 3：反例（评测做错了）

场景（假设示例，仅演示错误，未实测）：跑了 5 个自己挑的简单任务，全过，就说“新模型比上版强 20%”，还拿这个数和厂商自测分对比。

错在哪：第一，5 个任务样本太小，通过率波动大。第二，只挑简单的，任务有偏。第三，评分标准是跑完才定的，等于先看结果再定标准。第四，拿自己的分数和厂商自测分对比，harness 和任务都不一样，对比无效。第五，“强 20%”这个数没有计算过程，编出来的。

正确做法：20 到 50 个真任务，覆盖 3 到 5 类，口径跑前冻结，每个任务跑一次，失败也记，按类算通过率，结论写“在这批任务上通过率是 X”，不写“这个模型就是 X 水平”。

失败回滚

冒烟请求失败：

  • 401：Key 缺失或无效，检查 Key，不要重试同一把坏 Key。
  • 402：余额不足，先充值再重试。
  • 其他 4xx：先改请求，不要盲目重试。
  • 408 / 429 / 5xx：等一等再重试，重试加退避。

Harness 升级失败：用备份的旧配置回退到升级前版本，切换本身不用回退（服务端 checkpoint 不受你本地 Harness 版本影响），记一条失败原因，再升级。

搜索质量不达标：不把直调接进生产，继续用免费的服务端工具调用，或先不用搜索功能。不要为了“用上新功能”而接一个不好用的功能。

评测结果不好：记下来，不要改标准重跑。结果不好本身就是信息。改标准重跑，等于把信息扔了。

常见坑（6 条）

  • “模型名不用改 = 不用验证”：错。代码不用改，验证不能省。冒烟 + 计费核对 + 功能冒烟，三步都要走。
  • “免费窗口 = 全部免费”：错。免费的是经 Harness、Claude Code、Codex 的服务端工具调用。自己直调 API 按次计费。
  • “计费开始时间只记一个”：错。公告写 2026-10-31 16:00 UTC，文档写北京时间 11-01 00:00，两者是同一时刻。记错时区就记错截止日。
  • “搜索摘要 = 答案”：错。摘要是线索，关键结论打开原文验。
  • “厂商自测分 = 我的分数”：错。harness 不同、任务不同，分数不直接对比。基准分全部标注厂商自测、非独立复现，不只讲赢的项。
  • “评测跑完改标准”：错。跑后改标准等于白跑。标准跑前冻结，失败也记。
