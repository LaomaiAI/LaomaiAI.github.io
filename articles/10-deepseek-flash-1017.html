零迁移切换怎么做：改什么、不改什么、怎么验证

这次切换最省事的地方，就是代码不用动。

不改什么

  • 模型名不用改。继续写 deepseek-flash。来源：官方定价页。
  • 旧别名不用改。旧别名 deepseek-v4-flash、deepseek-v4-flash-vision-exp 仍接受，由同一 checkpoint 服务，按 Flash 价格计费。等于旧 checkpoint 已不再单独提供，你发到旧别名的请求，现在走的也是新 checkpoint。来源：官方定价页注脚。
  • Base URL 不用改。OpenAI 格式 https://api.deepseek.com，Anthropic 格式 https://api.deepseek.com/anthropic。来源：官方定价页。
  • Key 和请求格式不用改。同 OpenAI / Anthropic 兼容格式。
  • 接入工具不用改。二手来源称，API 可在 Claude Code、GitHub Copilot、OpenCode 中免改代码接入。本文未实测，接入前请按你用的工具实际验证。

要改什么：只改 Harness 版本

把 DeepSeek Harness 升级到 v0.2.1-rc.1 或更新。来源：官方公告。这一步不改代码，只改你本地跑任务的工具版本。

验证方法：三步冒烟

切完别直接上生产任务，先跑三步冒烟：

第一步：确认请求通了，且走的是 Flash 计费。发一条最小的聊天请求，看返回体 model 字段是否回显 deepseek-flash，HTTP 是否 200。再到账单或用量页核对，这次调用是否按 Flash 价格计费。旧别名请求的计费也应显示为 Flash 价格。

import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

resp = client.chat.completions.create(
    model="deepseek-flash",
    messages=[{"role": "user", "content": "用一句话说：你是谁？"}],
)
print(resp.model)
print(resp.choices[0].message.content)
print("input tokens:", resp.usage.prompt_tokens, "output tokens:", resp.usage.completion_tokens)

Anthropic 格式的 Base URL 是 https://api.deepseek.com/anthropic，模型名同样写 deepseek-flash。来源：官方定价页。

第二步：功能冒烟，各跑一条。工具调用一条，长上下文一条，视觉输入一条（官方定价页功能表标注 Flash 支持视觉输入）。来源：官方定价页。有一条不通，先停下来定位，别带着问题往下走。

第三步：升级 Harness 后，跑一条端到端小任务。比如让它从零做一个小网页或小游戏，跑通一次，确认新 checkpoint + 新 Harness 在你的环境里能完整走完一轮。这一步是为后面的自跑评测热身，不是评测本身。

Search & Fetch 怎么用：代码 + 免费窗口 + 成本算账

Search API 负责按 query 找网页，返回结构化结果；Fetch API 负责抓单个网页，返回 Markdown 正文。两个都是原始 JSON API，用和 DeepSeek API 同一个 Bearer Key。来源：官方 Search & Fetch 文档。

代码：直接调 API

import os
import requests

BASE = "https://api.deepseek.com"
HEADERS = {
    "Authorization": f"Bearer {os.environ['DEEPSEEK_API_KEY']}",
    "Content-Type": "application/json",
}

# 1. 搜索：query 必填，1 到 128 个 Unicode 字符；count 默认 10，范围 1 到 50
search = requests.post(
    f"{BASE}/v1/tools/search",
    headers=HEADERS,
    json={
        "query": "DeepSeek V4.1-Flash-1017 site:github.com lang:en after:2025",
        "count": 5,
        "need_content": False,  # 只想要摘要时保持 False；想要正文再开 True
    },
    timeout=30,
)
search.raise_for_status()
for r in search.json()["results"]:
    print(r["rerank_score"], r["title"], r["url"])
    print(r["summary"])

# 2. 抓取：url 必填，HTTP/HTTPS，不含用户名密码，最长 8192 字符
fetch = requests.post(
    f"{BASE}/v1/tools/fetch",
    headers=HEADERS,
    json={"url": "https://api-docs.deepseek.com/news/news261017"},
    timeout=30,
)
fetch.raise_for_status()
page = fetch.json()
print(page["title"])
print(page["content"][:2000])

参数口径以官方文档为准：query 支持 site:、-site:、-、-"..."、"..."、lang:、after:、before: 等算子；count 只控制返回条数，不影响单价；need_content 为 false 时 content 恒为空串；返回结果带 rerank_score（0 到 3，1.5 以上算高质量）、authority（0 到 4，3 以上为高权威，-1 为未知）、date（RFC 3339，UTC，未知为 null）。来源：官方 Search & Fetch 文档。

免费窗口：到点就开始计费

先分清两条链路，计费不一样：

  • 链路 A：你自己直接调 API。POST /v1/tools/search、POST /v1/tools/fetch，每次成功调用计费。
  • 链路 B：服务端工具调用。在 DeepSeek Harness、Claude Code、Codex 里让模型自己调搜索工具。计费开始前，对 DeepSeek API 用户免费。

计费开始时间，官方公告与官方文档是同一个时刻的两种写法：公告写 2026-10-31 16:00 UTC，文档写北京时间 2026-11-01 00:00。两者一致。来源：官方公告 + 官方 Search & Fetch 文档。

写稿日是 2026-10-18，免费窗口还剩约 13 天。顺序别反了：免费窗口内先用链路 B 验证搜索质量，确认有用，再把链路 A 接进自己系统。等到开始计费才想起来验证，就只能花钱验证了。

成本算账：搜索费和模型费分开算

搜索 / 抓取费：每个端点 $0.75 / 1,000 次成功调用，Search 和 Fetch 各自计。计费规则比你想的宽松一点：只有返回 HTTP 200 且有结果才计费。Search 必须返回非空 results，Fetch 必须返回正文内容。失败请求、空搜索结果、超时都不计费。来源：官方 Search & Fetch 文档。

模型 Token 费：按官方定价页，deepseek-flash 按 1M token 计。输入缓存命中：闲时 $0.003，忙时 $0.006。输入缓存未命中：闲时 $0.15，忙时 $0.30。输出：闲时 $0.60，忙时 $1.20。忙时是周一至周五 01:00-04:00 和 06:00-10:00 UTC（不含中国法定节假日），其余时间都是闲时，忙时价格是闲时的两倍。来源：官方定价页。

两个算术示例，不是实测账单：

  • 搜索：每天 200 次搜索 + 100 次抓取，30 天共 9,000 次，费用是 9 x $0.75 = $6.75。
  • 模型：1M 缓存未命中输入（闲时）+ 1M 输出（闲时），费用是 $0.15 + $0.60 = $0.75。

别混在一起：搜索费按次，模型费按 token。算预算要两笔分开列，不要只算一笔就说便宜。搜索量大的系统，搜索费可能超过模型费，反过来也一样，看你的用量结构。

限速与错误：接进系统前先看这张表

每个账号，Search 和 Fetch 各限 5 QPS，互不占用。Fetch 还有额外的单域名 QPS 限制。超限返回 429。来源：官方 Search & Fetch 文档。

错误处理按官方文档：408、429、5xx 等一等再重试；402 是余额不足，先充值再重试；其他 4xx 别盲目重试，先改请求。Fetch 的 404 可能是目标站不可用、被站方策略拦了、目标站报错、不支持的内容类型、或抓不到可用 Markdown。Fetch 还受目标站的可达性和访问策略限制。来源：官方 Search & Fetch 文档。

两个实操提醒：第一，搜索 query 会发给搜索引擎，别把密钥、内部链接、私密内容写进 query。第二，搜索摘要不是最终答案，关键结论要打开原文验，见下文“什么时候不该用”。

拿自己 20 到 50 个真实任务对照评测：方法

厂商的分数不是你的分数。厂商自测是在厂商的 harness 上，用厂商的任务跑的。你的任务、你的 harness、你的验收标准都不一样。所以发布当天最该干的第三件事，是跑你自己的评测集。

第一步：选任务，从真实活里挑

从你过去两周真实接过的活里挑 20 到 50 个，覆盖你最常做的 3 到 5 类，每类至少 5 个。不要只挑简单的，也不要只挑你擅长的。每个任务写清三样东西：输入是什么、期望交付物长什么样、验收点是什么。验收点要具体到能判通过还是不通过，比如“接口跑通且返回正确字段”，而不是“效果不错”。

第二步：冻结口径，跑之前全部定死

任务清单、提示词、评分表、harness 版本，写进一个文件，跑之前不再改。评分表至少包含：通过 / 不通过、失败原因（理解错需求、工具调用失败、输出格式错、中途卡住、其他）。冻结的意思是：跑完不许改评分标准。跑后改标准，等于白跑。

第三步：跑，同一环境，每个任务一次

同一 harness、同一配置，每个任务跑一次。失败不重跑到过。记录四样东西：checkpoint 名（DeepSeek-V4.1-Flash-1017）、日期、harness 版本、原始输出和耗时。原始日志留着，别只留结论。

第四步：算，按类分别算，不只算总通过率

总通过率只看一个数，会藏问题。按类分别算通过率，失败按原因归类。哪个类掉得多、哪种失败原因最常见，这才是你真正的信息。比如工具调用失败集中在某一类任务上，那说明问题在工具链，不在模型本身。

防自欺三条

  • 评分标准跑前定，跑后改等于白跑。看到结果不好就改标准，是最常见的自欺。
  • 失败也记。失败才是你真正的信息。只报通过的项，等于没评测。
  • 换 harness 就重跑。不同 harness 的分数不直接对比。旧 checkpoint 现在已由新 checkpoint 服务，你这次跑的结果就是新基线。以后新版本发布，用同一套任务再跑，对比才有意义。不要拿这次的结果和厂商自测分直接对比，harness 不同，任务不同。

样本量提醒

20 到 50 个任务，通过率上下波动大。差 5 个百分点以内，别急着下结论。评测集小的时候，一个任务的成败就能拉动几个百分点。结论要留有余地，写“在这批任务上通过率是 X”，不要写“这个模型就是 X 水平”。

第一，harness 不同，别直接对比分数。厂商自测分、别人的评测分、你的评测分，harness 不同就不直接对比。对比之前先对齐 harness、任务、评分标准，对不齐就别对比。
