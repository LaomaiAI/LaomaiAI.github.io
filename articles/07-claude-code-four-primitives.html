先问一句：这事谁拿计划？

答不上来，写再多提示词也是乱堆。

Skill 是方法，子代理是干活的人，Hook 是保证，Workflow 是脚本拿计划。

信息差：英文区已讲透“谁拿计划”，中文区还停留在“四种东西有什么区别”

问题：两种堆法，都在烧钱烧上下文

常见两种典型的堆法。第一种，把所有要求往 CLAUDE.md 里塞：不许碰 .env、部署流程、代码规范、测试步骤，全塞进去。文件越来越长，每次请求都全量进上下文，钱照烧，第十次还是有人把密钥文件改了。

第二种，什么事都上子代理：查个日志开三个 Agent，改两行代码也要拉个团队。窗口倒是干净了，账单和等待时间一起上去了。

两种堆法的根因是同一个：没分清四个东西到底谁拿计划、谁保证执行、成本落在哪。分清了，选型就是一道送分题。

结论先行：两问定选型

第一问：谁拿计划？Skill 里是 Claude 拿着你的文字照做；子代理是第二个 Claude 在自己的窗口拿计划；Workflow 是脚本拿计划，Claude 只看最终结果；Hook 是没人拿计划——事件一到，代码就跑。

第二问：要不要保证执行？CLAUDE.md、规则、Skill 都是“请求”，Claude 可以商量；Hook 是“保证”，事件触发就执行，退出码 2 还能把动作拦下来。

记住这两问，后面所有选型都不用背。

证据一：八个原语，一张表看清

英文区作者 Remy 在 2026 年 9 月 21 日的长文里，把官方文档分散在六个对比标签页、三页内容里的东西，收进了一张八原语决策表。下面是按他的表意译的核心四行，加上其余四个原语的定位（完整表见文末来源）：

原语谁触发在哪跑成本落在哪能保证什么
CLAUDE.md会话开始，一直在你的窗口每次请求，全程保证不了，只是上下文
Skill你敲 /名字，或 Claude 匹配描述你的窗口描述一直在，完整正文用时才加载保证不了，Claude 解读执行
子代理Claude 委派，或你 @ 它它自己的窗口只回摘要到主窗口隔离：主窗口保持干净
Hook生命周期事件触发Claude 之外不回输出就是零成本它一定跑，每次都跑
Workflow你跑保存好的命令脚本，后台多个 Agent，一份结果回主窗口脚本拿计划，不是 Claude
规则 / 插件 / Agent 团队规则：会话开始或文件命中；插件：安装后；Agent 团队：你要求组队（实验性）规则在你的窗口；插件随其内容；团队是多个完整会话规则按需；插件是其零件之和；团队是每人一个完整上下文规则保证不了；插件是打包箱；团队的同伴可以互相争论

同一篇文还引用了一项研究：2,853 个带 Agent 配置文件的公开仓库里，90.6% 只有 CLAUDE.md 这类上下文文件，5.5% 有 Skill，4.6% 有子代理（作者引用的 arXiv 2026 年 2 月研究）。大多数团队写下规范就停了，后面三件套根本没用上。

证据二：那个“十次里翻一次车”的 .env 故事

Remy 讲了自己的真实教训：他的 CLAUDE.md 里长期有一行“绝不碰 .env”，十次里大概九次都管用。听着不错，直到第十次改写了密钥，他不得不去轮换密钥。后来他把这四个字挪进了 PreToolUse Hook：路径一匹配就退出码 2，直接拒写。在他自己的叙述里，翻车率归零。

这不是说 CLAUDE.md 写错了，是放错了地方。需要“每次必拦”的事，就不该放在一个“可以商量”的地方。这是全文最值钱的一句话：不是提示词写得不好，是放错了原语。

证据三：Skill 是方法，子代理是干活的人

devpedia 的 Claude Code 教程把最常见的混淆点破了：Skill 专精的是方法——“这类任务来了，按这个配方走，用这些资源、模板、校验”；子代理专精的是执行者——“把这个问题交给一个专为这活搭的 Agent，它有自己的上下文，常常还有自己的工具限制”。

它的决策表很实用，直接抄：

如果你的价值在……用
输出格式 / 模板Skill
专精一个角色（探索、审安全、做规划）子代理
打包好的示例、模板、脚本Skill
把探索和分析挡在主线程之外子代理
必须每次都跑，不依赖模型“决定”跑不跑Hook
一条短而稳定的项目规则CLAUDE.md

而且它提醒了一句组合打法，后面实操会直接用：子代理探索找规律 → Skill 把分析定成固定格式输出 → Hook 在收尾前校验结果。三件套各干各的，不抢活。

证据四：Workflow 和“耐久边界”——别拿它当流水线

一份 2026 年 10 月 3 日的 Agentic Coding 研究笔记（kruxia/foundry）盘点了 Claude Code 当时的内置编排能力：子代理嵌套与 worktree 隔离、动态 Workflow（JS 脚本编排）、Agent 视图 / 后台会话、实验性的 Agent 团队、/goal 与 /loop（会话内调度）、跨会话消息、channels、云端会话与 Projects（公开测试版）、routines（云端 cron、API、GitHub 事件触发，研究预览）、GitHub Actions、检查点与回退。

同一份笔记也划清了耐久边界，写文时必须照实转述：Workflow 不接受中途用户输入、只能在会话内续跑；后台会话是本地的，关机就停；/loop 任务 7 天过期；Agent 团队不能恢复队友；routines 是即发即弃式会话，有每小时上限；成本数据是按会话估算的。笔记作者的结论是：目前没有第一流的、可跨多天多阶段、带人工审批门和跨会话预算治理的耐久流水线——那仍是编排器自己的活。

这句话直接决定了 Workflow 的定位：它是“一次跑完、脚本拿计划”的批量活，不是“挂一周、中间随时审批”的流水线。拿它当流水线，迟早被 7 天过期和关机停跑教做人。

实操：四步决策 + 三份可复制模板

下面是直接能用的流程。先走四步，再按需复制模板。模板按英文区公开教程整理，未逐条实测；跑之前按文末检查表对照官方文档核对一遍，尤其是你用的版本。

1

问谁拿计划

需要“照着固定流程走”→ Skill；需要“派个人去干”→ 子代理；需要“脚本说了算、批量跑”→ Workflow；需要“事件一到就执行”→ Hook。

2

能商量 → Skill / 子代理 / CLAUDE.md。不能商量（拦危险写、跑格式化、记日志）→ Hook，退出码 2 拦停。

3

CLAUDE.md 全程花钱，别塞流程；Skill 按需加载；子代理只回摘要；Workflow 批量才划算。

↓
4

组链，不单点

默认组合：子代理探索 → Skill 定格式 → Hook 验收。需要批量时，把整条链放进 Workflow 的脚本里。

模板 A：Skill 骨架（.claude/skills/<名字>/SKILL.md）

---
name: review-pr
description: 拉取 PR 差异，按检查表出评审结论。触发：评审、PR、review。
---

# 评审 PR

## 什么时候用
有人说“评审这个 PR”时用。

## 流程
1. 拉取差异，只看本次改动，不翻旧账。
2. 按检查表逐项过：架构、性能、模式、质量。
3. 每项给结论：通过 / 阻塞 / 待确认，并贴出对应 diff 行。

## 检查表
- [ ] 没有把密钥、Token 写进代码
- [ ] 危险操作有确认或回退
- [ ] 改动有测试或说明为什么不用测

## 输出格式
结论一句话 + 阻塞项列表 + 待确认项列表。不要写散文。

模板 B：子代理定义（.claude/agents/code-reviewer.md，按公开教程的 frontmatter 写法）

---
name: code-reviewer
description: 按架构、性能、模式、质量评审代码。实现功能后或评审改动时主动使用。
tools: Read, Glob, Grep, Bash
model: opus
skills:
  - code-review
---

你是代码评审员。只读改动，只回结论：阻塞项、待确认项、通过项。
不要顺手改代码。评审完就停。

写法要点来自 devpedia：子代理用 Markdown + frontmatter 定义，不继承完整系统提示；内置的有 Explore（只读快搜）、Plan；常见自定义角色是 code-reviewer、debugger、planner、test-runner、security-auditor、docs-writer。

模板 C：Hook（.claude/settings.json，PreToolUse 拦写 + PostToolUse 自动格式化）

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": ".claude/hooks/block-sensitive-writes.sh" }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [{ "type": "command", "command": "npx eslint --fix $(jq -r '.tool_input.file_path')" }]
      }
    ]
  }
}

block-sensitive-writes.sh 的核心逻辑：路径命中敏感文件（如 .env）时，向 stderr 写原因并以 退出码 2 退出。按 devpedia 的说明：退出 0 是成功，退出 2 是阻塞错误，其他退出码都是非阻塞错误——退出 1 拦不住任何东西，这是经典 bug 来源。Hook 处理器分 command / http / prompt / agent 四种；常用事件有 SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、PostToolUseFailure、Stop、SubagentStop、Notification。官方事件列表在 2026 年 9 月已超 30 个，不是每个都支持退出 2 拦截，关键用途要去官方文档确认。

图 4：组合打法来自 devpedia。示例：/audit Skill 拉起安全 / 性能 / 风格三个子代理，Hook 做最终校验。

官方文档的组合示例里有现成的：Skill + 子代理——一个 /audit Skill 拉起安全、性能、风格三个子代理，在隔离上下文里并行干活；CLAUDE.md + Skill——CLAUDE.md 只留“按 API 规范来”一句话，完整风格指南放 Skill 里按需加载；Hook + MCP——改了关键文件，Hook 触发外部通知。照这个样子串，你的主窗口永远只收结论，不收过程。

□检查项怎么判
☐每个需求都问过“谁拿计划”能说出它属于 Skill / 子代理 / Hook / Workflow 中的哪一个
☐CLAUDE.md 里没有塞流程只留短而稳定的规则；流程已拆成 Skill

☐子代理有 frontmatter 与工具限制只读活只给读工具；评审员不顺手改代码
☐Workflow 没被当成流水线无中途输入、会话内续跑、关机停跑、/loop 7 天过期都已考虑
☐组合链完整探索 → 定格式 → 验收，三段都有归属，没有一段是“靠自觉”
☐每次模型升级后删一次先停用一周，无回归再删；不再挣位置的原语删掉（Remy 的建议）

常见坑：这五个地方最容易翻车

  1. 退出 1 当拦截用。拦不住。拦截必须退出 2，且要实测。
  2. Workflow 里等审批。Workflow 不接受中途用户输入。需要审批的活，拆出来放 Hook + 人工门，别塞进脚本里等。
  3. “1000 个 Agent、16 并发”当一成不变的数字背。这是官方 Workflow 文档口径，版本变化快，写方案时核对当前版本，别当成永久承诺。
  4. 把 Agent 团队当稳定功能规划。它是实验性的，且不能恢复队友。生产排期别依赖它。
  5. 抄了模板不核对版本。Hook 事件列表、子代理字段、Workflow 能力都在变，本文模板按 2026 年 9–10 月公开教程整理。跑之前对照你用的版本的官方文档核对一遍。
